# 코드 배치·소유권 판단 가이드

이 저장소는 모듈과 패키지를 **다른 축**으로 나눈다.
모듈은 방향(누가 누구를 알아도 되는가), 패키지는 주제(이 파일이 무엇에 관한 것인가).

이 스킬이 필요한 이유는 배치 실수가 조용하기 때문이다.
잘못 둬도 컴파일되고 테스트가 통과한다. 실제로 이 저장소에서 두 번 그랬고,
패키지를 나누고 나서야 순환으로 드러났다.

## 사용 상황

1. 새 클래스를 어디에 둘지 판단할 때
2. 기존 타입의 위치가 맞는지 검토할 때
3. "공통이니까 global 에" 라는 제안을 받았을 때
4. 새 유스케이스(예약 등)를 추가할 때
5. 순환 참조가 보고됐을 때
6. `build.gradle.kts` 에 의존성을 추가하려 할 때

---

## 용어 정의

| 용어 | 의미 |
|---|---|
| 공유 커널 | 여러 하위 개념이 함께 쓰고, 그중 **어느 쪽의 소유도 아닌** 값. `SupplierId`, `StayPeriod` |
| 유스케이스 패키지 | 하나의 기능이 사는 곳. `search`, `catalog` |
| global | 유스케이스가 늘어도 **늘지 않아야 하는 것**. "공통" 이 아니다 |
| 변화의 축 | 무엇이 늘어날 때 이 디렉터리가 늘어나는가 |

## Step 1. 모듈부터 정한다 — 방향이 먼저다

```
domain           의존성 0. 프레임워크 금지
application      유스케이스와 Port. Spring 의존 금지
storage          DB 어댑터
supplier-client  공급사 어댑터(ACL)
app              HTTP 진입점 + Composition Root
```

질문 순서:

1. 이 코드가 **외부 기술을 아는가**(HTTP, SQL, Jackson, Reactor)? → 어댑터 모듈
2. 유스케이스 흐름인가, Port 정의인가? → `application`
3. 공급사와 무관하게 항상 참인 규칙인가? → `domain`
4. 조립·설정·스케줄·지표인가? → `app.global.config`

**`domain` 에 무언가를 넣기 전에 반드시 확인한다.**
`domain` 의 compileClasspath 에는 jar 가 하나도 없다. 애노테이션 하나도 들어갈 수 없다.
넣고 싶다면 그 타입이 정말 도메인 규칙인지 다시 본다.

---

## Step 2. ⚠️ 소유권은 이름이 아니라 의존 방향으로 정한다

**이 저장소에서 두 번 틀린 지점이다.** 둘 다 이름의 연상으로 위치를 정한 결과였다.

```
StayPeriod 를 domain.offer 에 두었다
  근거: "숙박 기간이니까 숙박 상품"
  실제: InventoryRule 도 StayPeriod 를 받는다 → inventory ↔ offer 순환
  교정: 기간은 재고의 것도 상품의 것도 아닌 공유 값 → domain 루트

SupplierTargets 를 application.search 에 두었다
  근거: "검색이 쓰는 값이니까 검색"
  실제: CatalogSnapshot 이 이 타입을 반환한다 → catalog ↔ search 순환
  교정: 카탈로그가 검색에게 주는 계약 → application.catalog
```

판단 절차:

1. 이 타입을 **만드는** 쪽은 어디인가
2. 이 타입을 **읽는** 쪽은 어디인가
3. 만드는 쪽이 하나면 → 거기가 소유자다. 읽는 쪽이 참조한다
4. 만드는 쪽이 둘 이상이고 서로 모르면 → 공유 커널(상위 패키지)

**"누가 쓰는가" 가 아니라 "누가 만드는가" 로 정한다.**
쓰는 쪽으로 정하면 두 쪽이 쓰는 순간 순환이 생긴다.

## Step 3. "공통이니까 global" 을 거부한다

`global` 은 **유스케이스가 늘어도 늘지 않아야 하는 것** 만 둔다.

| 넣어도 되는 것 | 넣으면 안 되는 것 |
|---|---|
| 오류 응답 형식, 예외 핸들러 | 특정 유스케이스만 쓰는 헬퍼 |
| Composition Root, 설정 바인딩 | "지금은 하나뿐이니까" 인 것 |
| 스케줄러, 지표 어댑터 | 유스케이스 이름이 들어간 타입 |

판정 질문: **예약 유스케이스가 추가되면 이 파일이 커지는가?**
커진다면 `global` 이 아니라 유스케이스 패키지로 간다.

`global → 유스케이스` 참조는 ArchUnit 이 막는다(`global 은 유스케이스 패키지를 모른다`).
반대 방향(`search → global.error`)만 허용한다.

## Step 4. 변화의 축이 다르면 나누는 축도 다르다

`supplier-client` 만 다른 모양인 것은 일관성이 없는 게 아니라 같은 기준의 결과다.

```
application, app     변화의 축 = 유스케이스   → search/ catalog/ 로 나눈다
supplier-client      변화의 축 = 공급사       → a/ b/ 로 나눈다
```

새 디렉터리를 만들기 전에 묻는다. **무엇이 늘어날 때 이 디렉터리가 하나 늘어나는가?**
답이 "계층" 이면 잘못 나누고 있는 것이다.
계층으로 나누면 기능 하나를 고칠 때 여러 패키지를 왕복하고,
기능을 지울 때 무엇을 지워야 하는지 흩어진다.

---

## Step 5. 새 유스케이스를 추가할 때

예약이 들어온다면 이렇게 늘어난다.

```
domain/reservation/          예약 도메인 규칙
application/reservation/     ReservationService, Port
storage/reservation/         DB 어댑터
app/reservation/             컨트롤러 + dto/{request,response}
app/global/                  늘어나지 않는다  ← 이것이 지켜지는지가 판정 기준
```

`app/global` 이 커진다면 유스케이스 고유의 것을 거기 넣고 있는 것이다.

요청 DTO 는 `dto/request`, 응답 DTO 는 `dto/response` 로 나눈다.
서로 참조하지 않는다(ArchUnit). 한쪽이 다른 쪽 타입을 재사용하면
입력 계약을 고칠 때 출력 계약이 함께 바뀐다.

유스케이스 입력은 `application` 의 command 타입으로 한 번 옮긴다.
HTTP DTO 를 `application` 으로 넘기면 웹 계약이 유스케이스 계약이 된다.

---

## Step 6. 순환이 보고되면 도구를 의심하지 않는다

ArchUnit 이 순환을 보고하면 **거의 항상 모델링 문제다.**
순환을 없애려고 인터페이스를 하나 더 만드는 것부터 하지 않는다.

```
1. 순환에 참여한 타입을 전부 적는다
2. 각각에 대해 Step 2 를 적용한다 — 만드는 쪽이 어디인가
3. 소유권이 틀린 타입을 옮긴다
4. 그래도 남으면 그때 경계 타입 도입을 검토한다
```

3번에서 대부분 풀린다. 이 저장소의 두 순환 모두 파일 하나를 옮겨서 해결됐다.

**순환 검사의 슬라이스를 모듈이 아니라 패키지 단위로 잡아 둔 이유가 이것이다.**
모듈 단위면 Gradle 이 이미 막는 것만 다시 검사하는 셈이라 아무것도 못 찾는다.

---

## Step 7. 의존성을 추가하기 전에

`build.gradle.kts` 에 한 줄을 넣기 전에 확인한다.

- `domain` 에는 어떤 것도 추가하지 않는다. BOM 외에 jar 가 없는 것이 설계 진술이다
- `application` 에 Spring 을 추가하지 않는다. `@Service` 를 붙이고 싶어지면 그것이 신호다
- 어댑터 모듈에는 추가해도 된다. 어댑터는 정의상 프레임워크와 붙는 계층이다
- 추가한 의존성이 **어느 방향으로 새는지** 본다. `api` 로 넣으면 소비자에게 전파된다

`application` 만 `java-library` 인 이유는 Port 시그니처의 `Mono` 와 결과 타입이
소비자에게 보여야 하기 때문이다. 다른 모듈은 `implementation` 으로 가둔다.

## Step 8. 검증

배치를 바꿨으면 확인한다.

```bash
./gradlew clean check          # ArchUnit 8개 포함
```

- `패키지_사이에_순환_참조가_없다`
- `global_은_유스케이스_패키지를_모른다`
- `요청_DTO와_응답_DTO는_서로를_참조하지_않는다`
- `정규화는_순수_함수_영역이다`
- `공급사_DTO는_자기_모듈_밖으로_나가지_않는다`
- `컨트롤러는_어댑터에_의존하지_않는다`
- `domain_은_프레임워크에_의존하지_않는다`

문서에 적힌 경로가 낡지 않았는지도 본다.
`docs/traceability.md` 와 `docs/architecture.md` 가 클래스 경로를 인용한다.

## 답변 원칙

- **"공통이니까 common/global 에" 라고 답하지 않는다.** 예약이 추가되면 커지는지 먼저 묻는다.
- 위치를 정할 때 **"누가 쓰는가" 가 아니라 "누가 만드는가" 로 정한다.**
- 순환이 보고되면 **인터페이스를 추가해 끊기 전에 소유권부터 다시 본다.**
- 새 디렉터리를 제안하기 전에 **"만들지 않는다"(기존 패키지에 둔다)를 후보로 넣는다.**
  파일이 셋뿐인 패키지는 이름만 늘린 것일 수 있다.
- 배치를 바꾸면 **문서의 클래스 경로도 같이 고친다.** 스크립트가 대조하지 않는 부분이다.
- 규칙을 새로 만들자는 결론이 나오면 기준을 적용한다 —
  **어겼을 때 컴파일이 되고 테스트가 통과하며 런타임에도 아무 일이 없는가.**
  그런 것만 규칙으로 만든다.
