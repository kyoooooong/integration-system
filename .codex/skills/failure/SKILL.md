# 실패 분류·격리 가이드

이 저장소에서 **가장 많이 틀린 영역**이다. 두 번 잘못 분류했고 둘 다 조용히 동작했다.
이 스킬은 같은 실수를 반복하지 않기 위해 쓴다.

## 사용 상황

1. 새 예외를 어떻게 분류할지 판단할 때
2. 실패를 어느 단위에서 격리할지 정할 때
3. HTTP 상태 코드를 정할 때
4. "서버가 중간에 죽으면?" 을 검토할 때
5. 라이브러리 기본값이 우리 타임아웃과 어떻게 상호작용하는지 확인할 때

---

## Step 1. 이 실패는 누구 것인가

**가장 먼저 묻는다. 분류가 여기서 갈린다.**

| 질문 | 답이 "우리" 면 | 답이 "공급사" 면 |
|---|---|---|
| 이 실패를 없애려면 누가 무엇을 해야 하는가 | 우리 코드·설정을 고친다 | 공급사에 문의한다 |

**공급사 성공률 지표에 우리 문제가 섞이면 그 지표는 아무 의미가 없다.**

| 상황 | 분류 | 왜 |
|---|---|---|
| 공급사 5xx | `UNAVAILABLE` | 공급사가 죽었다 |
| 공급사 429 / rate limit 코드 | `RATE_LIMITED` | 공급사가 제한했다 |
| **공급사 4xx** | **`INTERNAL_ERROR`** | 공급사는 정상 동작하면서 "네 요청이 잘못됐다" 고 답했다. 우리 문제다 |
| 응답이 계약에 안 맞음 | `INVALID_RESPONSE` | 공급사가 이상한 걸 줬다 |
| 응답이 제시간에 안 옴 | `TIMEOUT` | 공급사가 느리다 |
| **우리 동시성 상한에 걸림** | **`LOCAL_SATURATION`** | 우리가 정한 한계다 |
| **우리 커넥션 풀 고갈** | **`LOCAL_SATURATION`** | 공급사는 아무 잘못이 없다 |
| 우리 코드 버그 | `INTERNAL_ERROR` | — |
| 매핑이 없어 호출조차 못 함 | `CATALOG_UNAVAILABLE` | 우리 카탈로그가 낡았다 |

## Step 2. ⚠️ 상속을 조심한다 — 실제로 여기서 틀렸다

```java
PoolAcquireTimeoutException extends java.util.concurrent.TimeoutException
```

`instanceof TimeoutException` 으로 분류하면 **우리 커넥션 풀 고갈이 공급사 타임아웃으로
집계된다.** 자기 유발 장애를 공급사 탓으로 돌리면 대응이 "공급사에 문의" 로 흘러가고
실제 원인인 우리 동시성 설정은 손대지 않는다.

**포화 판정을 타임아웃 판정보다 앞에 둔다. 순서가 곧 의미다.**

새 예외를 분류할 때는 항상 확인한다.

```bash
javap -cp <jar> <ExceptionClass> | head -2   # 무엇을 상속하는가
```

---

## Step 3. ⚠️ 라이브러리 기본값이 우리 타임아웃보다 긴지 확인한다

**같은 함정이 두 곳에 있었고 한 곳만 고쳤다가 나중에 나머지를 찾았다.**

| 라이브러리 | 기본값 | 우리 타임아웃 | 결과 |
|---|---|---|---|
| Reactor Netty 획득 대기 | **45s** | 응답 2s | 풀 고갈이 "공급사 타임아웃" 으로 기록 |
| Hikari `connectionTimeout` | **30s** | async 10s | 서블릿 스레드가 30초 묶임. 끊을 장치 없음 |

**새로운 풀·큐·클라이언트를 도입하면 반드시 이 표에 한 줄을 추가한다.**

확인 방법은 문서를 읽는 게 아니라 **라이브러리에서 직접 읽는 것**이다.

```java
System.out.println(ConnectionProvider.DEFAULT_POOL_ACQUIRE_TIMEOUT);
System.out.println(new HikariConfig().getConnectionTimeout());
```

그리고 **어느 타임아웃이 그 구간을 실제로 관장하는지** 확인한다.
`spring.mvc.async.request-timeout` 은 **비동기 구간만** 관장한다.
`Mono` 조립 전 서블릿 스레드에서 도는 동기 코드에는 적용되지 않는다.

## Step 4. 500 인가 503 인가

**500 은 "재시도하지 마라" 라는 뜻이다.**

```
INTERNAL_ERROR    코드가 틀렸다.   다시 보내도 같다.        500
LOCAL_SATURATION  자원이 부족했다. 잠시 뒤엔 될 수 있다.    503
DB 커넥션 풀 고갈  일시적 용량 문제.                        503
DB 다운           의존성이 지금 사용 불가.                  503
```

"우리 잘못" 이라는 이유만으로 500 을 주지 않는다.
소유권(지표용)과 재시도 가능성(HTTP 용)은 **다른 축**이다.

전체 매핑:

```java
if (hasUsableSupplier())              return 200;   // ← 상태 기반. offers.isEmpty() 아님
if (hasDeterministicBug())            return 500;
if (allFailuresAre(TIMEOUT))          return 504;
if (allFailuresAre(INVALID_RESPONSE)) return 502;
return 503;
```

**502/504 는 동질 실패일 때만.** 혼합에서 어느 하나를 우선할 근거가 없다.

**`hasUsableSupplier()` 를 `offers.isEmpty()` 로 판정하면** 전 숙소가 만실인 성수기에
503 이 나간다. "결과 없음" 과 "조회 실패" 를 구분하려고 만든 로직이 정반대로 동작한다.

## Step 5. 어느 단위에서 격리하는가

| 오류 | 단위 | 이유 |
|---|---|---|
| 커넥션·타임아웃·HTTP 5xx | **batch** | 응답 자체가 없다 |
| 본문 코드 실패 | **batch** | 공급사가 실패를 선언했다 |
| JSON 문법 오류·타입 변환 실패 | **batch** | 역직렬화 이전·중. `bodyToMono(DTO)` 로는 item 격리 불가 |
| 성공 코드인데 data 가 null | **batch** | 응답 수준 계약 위반 |
| currency 누락·날짜 이상·매핑 없음 | **item** | DTO 는 만들어졌다 |

> **역직렬화에 성공한 item 의 의미적 검증 실패만 item 단위로 격리한다.**

**문서가 코드보다 낙관적이면 그건 거짓말이다.** 이 표를 바꾸면 테스트도 같이 바꾼다.

### Reactor 에서 조용히 깨지는 세 지점

```java
// ① onErrorResume 은 flatMap 안쪽. 바깥이면 첫 실패가 나머지 배치를 취소한다.
.flatMap(batch -> call(batch).onErrorResume(e -> Mono.just(failure(batch, classify(e)))),
         concurrency)

// ② empty 는 에러가 아니라 onErrorResume 이 못 잡는다.
//    없으면 그 배치가 성공도 실패도 아닌 채로 사라진다.
.switchIfEmpty(Mono.error(...))

// ③ transform 이 아니라 transformDeferred.
//    transform 은 조립 시점에 한 번만 평가되어 상한이 안 걸리는데 코드는 걸린 것처럼 보인다.
.transformDeferred(BulkheadOperator.of(bulkhead))
```

## Step 6. 정상 빈 결과와 사용 불가를 타입으로 나눈다

```
items == []                → Success   공급사가 조건에 맞는 상품이 없다고 정상 응답했다
items != [] && offer >= 1  → Success   일부 item 거부는 허용
items != [] && offer == 0  → Failure   응답은 왔는데 하나도 쓸 수 없다
```

`boolean success` 로 두면 "배치 1은 503, 배치 2는 전부 거부" 가 PARTIAL 로 집계되는
버그가 난다. **의미를 가장 안쪽 경계에서 정확히 정하면 바깥 집계가 단순해진다.**

---

## Step 7. 장애의 순간을 전부 적는다

다단계 상태 변경이 있으면 **각 단계 사이**를 하나씩 적는다.

```
1 → 2 사이 종료?   2 → 3 사이 종료?   커밋 직전?   커밋 직후?
```

파생 데이터를 도입한다면 **그것이 유실될 때**를 반드시 다룬다.
캐시라면 "인메모리인데 날아가면?" 이고, 답은 보통 **데이터 손실이 아니라 부하 증폭**이다.
그리고 **"캐시가 사라지면 원본이 대신 받는다" 는 원본이 그 부하를 감당할 때만 참이다.**

**이상적인 결론은 "보상 코드가 필요 없다" 이고, 그것은 복구 코드를 잘 짜서가 아니라
부분 상태 자체를 만들지 않아서 얻어진다.** 카탈로그 전체 스냅샷 단일 트랜잭션이 그 예다 —
장애표의 모든 칸이 "롤백" 이 되면서 보정 배치도 좀비 정리도 재개 offset 도 사라졌다.

---

## Step 8. 인프라 예외를 위로 올려보내지 않는다

`DataAccessResourceFailureException` 같은 저장소 기술의 예외가 컨트롤러까지 가면
**포트 경계가 의미를 잃는다.** 포트 경계에서 애플리케이션 개념으로 번역한다.

app 모듈에서 그 예외 타입을 import 하려는데 컴파일이 안 된다면 **그것이 옳은 신호다.**
의존성을 추가해서 뚫지 말고 번역한다.

## Step 9. 검증

**실패 처리는 경과 시간으로 검증하지 않는다.**

| 검증하고 싶은 것 | 틀린 방법 | 맞는 방법 |
|---|---|---|
| 병렬 호출 | `time curl` | 서버의 요청 도착 시각 / 동시 진입 수 |
| 동시성 상한 | 총 소요 시간 | 서버에서 동시에 들어와 있는 요청 수를 직접 센다 |
| 서킷이 열렸는가 | 빨라졌는가 | upstream 호출 수가 0인가 |
| 부분 실패 격리 | 응답이 왔는가 | 성공한 배치의 결과가 **남아 있는가** |

**반대 방향도 확인한다.** "전부 X 로 분류한다" 로도 통과하는 테스트는 X 를 검증한 게 아니다.
포화 테스트를 만들었으면 "공급사가 느린 것은 포화가 아니다" 도 함께 만든다.

주요 분류는 **일부러 지워서 테스트가 깨지는 것을 확인한다.**

## 답변 원칙

- **"예외 잡아서 로그 찍고 넘어가죠" 라고 답하지 않는다.** 그것이 누구 잘못인지,
  지표에서 어떻게 보일지, 클라이언트가 무엇을 해야 할지를 먼저 정한다.
- 가용성을 위해 catch 하되 **관측을 숨기지 않는다.** 관측 없는 catch 는 버그를 삼키는 catch 다.
- 새 `FailureType` 을 추가하기 전에 **기존 것으로 표현되지 않는지** 먼저 본다.
  사유가 늘어나야 하는 이유는 "다른 사람이 다른 행동을 해야 할 때" 뿐이다.
- 라이브러리 기본값을 인용할 때는 **직접 읽어서 확인한다.** 기억으로 답하지 않는다.
- 한 곳에서 함정을 찾았으면 **같은 패턴이 어디에 또 있는지 찾아본다.**
  전송 계층에서 찾고 DB 쪽을 안 봤다가 나중에 같은 문제를 발견한 적이 있다.
