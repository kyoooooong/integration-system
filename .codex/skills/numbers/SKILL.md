# 숫자에 근거 붙이기

이 저장소는 **숫자 하나마다 라벨과 출처를 요구한다.**
"통상 2초입니다", "일반적으로 50~100입니다" 는 답이 아니다. 그 문장에 출처가 없다.

## 사용 상황

1. 새 설정값을 추가할 때
2. 기존 값을 바꾸자는 제안이 나올 때
3. 성능 개선이나 튜닝 요청이 들어올 때
4. 라이브러리 기본값을 그대로 쓸지 명시할지 판단할 때

---

## Step 1. 라벨 5종 중 하나를 붙인다

| 라벨 | 의미 | 바꾸면 |
|---|---|---|
| `CONTRACT` | 프로토콜·계약이 정한 값 | **계약 위반** |
| `DESIGN_INVARIANT` | 우리 아키텍처 정책 | 설계 의도가 바뀜 |
| `MEASURED` | 실측 완료. 조건·명령·N 이 기록에 있음 | 재측정 필요 |
| `EVALUATION_DEFAULT` | 동작 검증용 초기값. **최적값 주장 아님** | 자유 |
| `PRODUCTION_TUNING` | 운영 지표와 SLO 로 산출 | 지표 재확인 |

**측정 전에는 절대 `MEASURED` 라고 쓰지 않는다.**

근거가 없으면 **"근거 없음" 이라고 쓴다.** 억지로 만들지 않는다.
safety factor("실측 × 2")의 배수도 숫자다. 경계 실험 결과를 남긴다.

---

## Step 2. ⚠️ 무엇을 측정할 수 있는지 먼저 구분한다

**상류는 우리가 만든 Mock 이다.**
따라서 "공급사가 실제로 얼마나 빠른가" 는 여기서 알 수 없고,
그 값으로 타임아웃을 정하면 **숫자에 가짜 출처를 붙이는 일**이 된다.

| 측정할 수 있는 것 | 측정할 수 없는 것 |
|---|---|
| 우리 동시성 상한이 실제 구속 조건인가 | 공급사 응답 시간 분포 |
| 포화가 시작되는 지점이 설정값으로 설명되는가 | 공급사 rate limit |
| 포화 상황에서 결과가 오염되는가 | 공급사 SLO |
| DB 조회 비용과 그 확장 곡선 | 실제 트래픽 패턴 |

`connect-timeout` 과 `response-timeout` 은 부하 테스트를 돌린 뒤에도
**`EVALUATION_DEFAULT` 로 남는다.** 그것들은 공급사에 대한 값이기 때문이다.

---

## Step 3. 개별 값보다 순서를 주장한다

**개별 값의 최적값을 주장할 근거가 없을 때, 값들 사이의 관계는 주장할 수 있다.**
그 관계가 **포화를 어느 계층에서 드러낼지**를 정한다.

```
batch-concurrency  ≤  bulkhead-max-concurrent-calls  <  max-connections
pending-acquire-timeout  <  response-timeout
hikari connection-timeout  <  spring.mvc.async.request-timeout
```

**앞 줄이 필요한 이유:** `batch-concurrency` 는 *요청 하나*의 상한이라 동시 검색 N 건이면
상류로 N 배가 나간다. 전송 계층 풀이 먼저 고갈되면 포화가 라이브러리 내부 예외로 드러나는데,
그 기본 풀 크기는 **호스트 CPU 수에 따라 달라진다.**
배포 환경마다 다른 한계는 근거로 삼을 수 없다.

**뒤 두 줄이 필요한 이유:** 라이브러리의 획득 대기 기본값이 우리 타임아웃보다 훨씬 길면,
고갈이 **다른 원인으로 위장된 실패**가 된다.

> **불변식은 주석이 아니라 생성자에서 검사한다.**
> 설정 오타로 포화가 엉뚱한 계층에서 드러나기 시작하면 지표를 아무리 봐도 원인을 알 수 없다.
> 런타임에 이상하게 동작하느니 기동을 실패시킨다.

## Step 4. 기본값을 쓸지 명시할지

기본값을 쓰는 것도 **결정**이고 근거가 필요하다. 두 질문으로 가른다.

| 질문 | 예 → 명시한다 | 아니오 → 기본값 |
|---|---|---|
| 기본값이 배포 환경에 따라 달라지는가 | 결정성이 없으면 근거를 댈 수 없다 | |
| 기본값이 우리 다른 타임아웃과 모순되는가 | 고갈이 다른 원인으로 위장된다 | |

**둘 다 아니오면 기본값을 쓰고 그 이유를 적는다.**
Hikari `maximum-pool-size` 10 은 그렇게 유지했다 —
측정한 조회 비용 기준으로 처리량이 우리 상한의 4배 이상이라 늘릴 근거가 없다.

라이브러리 기본값은 문서가 아니라 **직접 읽어서** 확인한다.

```java
System.out.println(ConnectionProvider.DEFAULT_POOL_MAX_CONNECTIONS);
System.out.println(new HikariConfig().getConnectionTimeout());
```

## Step 5. 숫자를 없앨 수 있는지 먼저 본다

> **"숫자에 근거를 붙여라" 의 최선은 숫자를 없애는 것이다.**

최대 숙박 기간 상한을 두지 않은 것은 "비용이 없다"는 뜻이 아니다.
현재 계약에 최대 숙박일이 없어서 30박/90박 같은 숫자를 만들지 않았을 뿐이다.
`nightCount()` 는 날짜 컬렉션을 만들지 않아 기간 계산 자체는 O(1)이지만,
Supplier 응답 크기와 일별 재고 검증 비용은 숙박일 수에 따라 늘 수 있다.
실제 최대 조회 기간이나 서비스 정책이 정해지면 입력 단계에서 제한한다.

새 숫자를 추가하기 전에 묻는다.

```
이 숫자가 막으려는 것이 무엇인가?
그것을 구조로 막을 수는 없는가?
```

## Step 6. 측정한다면 무엇을 어떻게

**executor 선택이 결과를 바꾼다.**

`ramping-vus` 를 쓰면 "최대한 빨리" 보내게 되어 **도착률이 시스템 응답 속도에 종속된다.**
포화가 시작되면 거부가 빨라져 도착률이 오히려 올라가고, 부하 생성기가 먼저 죽는다.
실제로 그렇게 만들었다가 macOS 임시 포트를 고갈시켰다(`errno 49`).

**`constant-arrival-rate` 로 도착률을 우리가 정해야 이론값과 대조할 수 있다.**

측정 전에 **이론값을 먼저 적는다.**

```
공급사당 처리량 상한 ≈ 동시 호출 상한 / 공급사 응답 시간
```

실측이 이론값과 맞으면 **설정한 상한이 실제 구속 조건**이라는 뜻이다.
훨씬 일찍 평탄해지면 다른 곳이 먼저 구속된 것이고,
훨씬 늦으면 상한이 걸리지 않고 있는 것이다. **둘 다 설정이 의미대로 동작하지 않는다는 뜻이다.**

측정 기록에는 반드시 남긴다.

```
호스트 / DB / 상류 조건 / 설정값 / 도구와 버전 / 단계별 결과 / 재현 명령
```

---

## Step 7. 확장 곡선은 한 점으로 주장하지 않는다

"수백 개 규모까지 유효하다" 같은 문장은 재 본 적 없는 문장이었다.
선형인지 하위 선형인지 주장하려면 **점이 최소 두 개** 있어야 한다.

네 점(500/2,000/4,000/8,000)을 재고 나서야
"하위 선형이다" 와 "8,000 에서도 DB 는 구속 조건이 아니다" 를 쓸 수 있었다.

그리고 그 측정이 **Revisit 조건을 문장에서 부등식으로 바꿨다.**

```
"측정된 병목이 생기면"  →  풀 크기 / 조회 시간 < 처리량
```

## Step 8. 실무 자료를 쓸 때

숫자를 머릿속에서 만들지 않기 위해 확인하되, **베끼지 않는다.**

| 확인할 것 | 하지 말 것 |
|---|---|
| 그 숫자가 **어떤 조건**에서 나온 값인가 | 값만 가져오기 |
| 우리 조건이 그 조건과 같은가 | 다른데 같다고 가정하기 |
| 그 결정을 **왜** 했는가 | 결론만 복사하기 |

업계의 10분 TTL 은 **예약 패널**의 값이다. 여정 단계별로 다르게 잡는 것이 핵심인데
그 축이 없는 곳에 숫자만 가져오면 **근거 없는 숫자가 하나 더 생긴다.**

**가져온 것과 가져오지 않은 것을 문서에 구분해서 적는다.**

````md
- 근거:

### 다른 값과의 순서 관계
```
...
```
- 생성자에서 검사하는가?

### 라이브러리 기본값
| 항목 | 기본값 | 우리 값 | 모순 여부 |

### 측정 가능한가
- 측정할 수 있는 것 / 없는 것
- 측정한다면 이론값은 얼마인가

### 잃는 것 / Revisit 조건
- ...
````

## 답변 원칙

- **"보통 이 정도 씁니다" 라고 답하지 않는다.** 그 문장에 출처가 없다.
- 새 숫자를 제안하기 전에 **"하지 않는다"(기본값 유지, 또는 구조로 제거)를 후보 한 행으로 넣는다.**
- 성능 개선 요청에는 **측정된 병목이 있는지 먼저 묻는다.**
  없으면 그 추가가 오버엔지니어링이라는 것을 근거와 함께 말한다.
- 라이브러리 기본값을 인용할 때는 직접 읽어서 확인한다.
- 값을 바꾸자는 결론이 나오면 **그 값이 참여하는 순서 불변식이 여전히 성립하는지** 확인한다.
- 측정 결과가 이론값과 다르면 **먼저 이론을 의심하고, 그 다음 측정 방법을 의심한다.**
  마지막에 코드를 의심한다.
