# 공급사 추가·수정 가이드

이 저장소의 확장성 주장은 **"공급사를 추가해도 오케스트레이션과 도메인 규칙은 바뀌지 않는다"**
하나다. 이 스킬은 그 주장이 깨지지 않게 하는 데 쓴다.

## 사용 상황

1. 새 공급사(C, D…)를 추가할 때
2. 기존 공급사의 응답 형식이 바뀌었을 때
3. 정규화에서 어떤 필드를 어떻게 다룰지 판단할 때
4. 공급사별 분기를 넣고 싶어질 때 (대부분 넣으면 안 된다)

---

## Step 1. 먼저 확인 — 이 변경이 어디까지 번지는가

새 공급사를 추가할 때 **건드려야 하는 것**:

| 대상 | 내용 |
|---|---|
| `supplier-client/…/c/` | DTO(전부 boxed), `CSearchAdapter`, `CCatalogAdapter`, `CNormalizer` |
| `SupplierIds` | 상수 한 줄 |
| `SupplierClientConfiguration` | `@Bean` 셋 (WebClient, SearchPort, CatalogPort) |
| `application.yaml` | 설정 블록 |

**절대 건드리면 안 되는 것**:

| 대상 | 건드려야 한다면 |
|---|---|
| `domain` 모듈 전체 | 표준 모델이 공급사를 알게 된 것이다. 설계가 틀렸다 |
| `SearchStaysService` | 오케스트레이션에 공급사별 분기가 들어간 것이다 |
| `CatalogSyncService` | 동기화가 공급사를 구분하게 된 것이다 |
| `SearchResponse` / API 계약 | 공급사 형식이 API 로 샌 것이다 |
| 기존 A·B 어댑터 | 새 공급사 때문에 기존 것을 고칠 이유가 없다 |

> **"이걸 고쳐야 하는데요" 라는 답이 나오면 거기서 멈추고 왜 그런지 먼저 설명한다.**
> 고치는 것보다 왜 고쳐야 하는지가 더 중요한 정보다.

ArchUnit `공급사 DTO 는 자기 모듈 밖으로 나가지 않는다` 가 이것을 강제한다.

---

## Step 2. 공통 골격을 쓴다

`AbstractSupplierSearchAdapter<R>` 를 상속한다. 공급사별로 다른 것만 구현한다.

```java
URI uriFor(UriBuilder, SearchCommand, List<String> batch)   // URI 모양
Class<R> responseType()                                      // 응답 타입
Mono<R> validateResponseEnvelope(R)                          // 봉투 해석
BatchResult normalizeAll(R, SearchCommand, List<String>, CatalogSnapshot)
```

**공통 골격을 복제하지 않는다.** 배칭·유계 동시성·타임아웃·Bulkhead·격리 단위가 거기 한 번만
있어야 한다. `onErrorResume` 의 위치나 `switchIfEmpty` 의 유무처럼 **한 줄만 틀려도 조용히
깨지는** 부분이 공급사 수만큼 늘어나면 안 된다.

벌크 상한은 어댑터 내부 상수다. 공급사 C 의 상한이 20이면 C 어댑터에 20이 들어가고
**오케스트레이터는 그 값을 모른다.** 설정으로 빼지 않는다 — 설정 실수 하나가 프로토콜 위반이 된다.

## Step 3. DTO 는 전부 boxed

```java
record CItem(String code, Integer maxOccupancy, Boolean taxIncluded, Long totalPrice) {}
```

primitive 면 Jackson 이 필드 부재를 `false`/`0` 으로 채운다.
그러면 **"공급사가 아무 말도 안 했다" 가 "공급사가 세금 미포함이라고 선언했다" 로 둔갑한다.**

`FAIL_ON_NULL_FOR_PRIMITIVES` 를 켜는 대안은 역직렬화 실패가 되어 **배치 전체를 죽인다.**

unknown property 는 무시한다(Jackson 3 기본값). 공급사의 필드 추가는 하위 호환 변경이고
그것이 우리 배치 실패가 되면 안 된다. 우리 DTO 필드명 오타는 boxed + 필수 필드 거부로
**시끄럽게** 드러난다.

**경계: 외부 DTO 는 boxed, 도메인은 primitive.**

## Step 4. 검증 순서를 지킨다

```
① identity 필드 존재       코드가 없으면 MISSING_REQUIRED_FIELD
② 요청 배치 소속           response ⊆ requested
③ 매핑 해석                UNMAPPED_PROPERTY / UNMAPPED_ROOM_TYPE
④ 동적 필수 필드           currency, 금액, 재고, 조식
⑤ 날짜 행                  InventoryRule (도메인)
⑥ 금액                     Money (도메인)
⑦ 재고 min
⑧ static drift 진단        거부 아님
```

**순서를 헬퍼로 감추지 않는다.** 순서 자체가 설계 진술이라 감추면 읽는 사람이 확인할 수 없다.

**①을 ③보다 앞에 두는 이유:** `resolve(null, "STD")` 를 먼저 하면 공급사 응답 문제가
`UNMAPPED_PROPERTY` 로 기록되어 **우리 카탈로그가 낡은 문제로 오진된다.**

**②의 계약은 `response ⊆ requested` 이지 `==` 가 아니다.**

```
요청했는데 응답에 없음      정상 (재고 없음 / 인원 조건 미달)
요청 안 했는데 응답에 있음   비정상. 카탈로그에 있어도 거부
```

`==` 로 검증하면 정상 상황을 계속 거부한다.

## Step 5. 필드 소스를 섞지 않는다

| 역할 | 필드 | 유일한 소스 | live 가 다르면 |
|---|---|---|---|
| 식별 | `propertyId`, `roomTypeId` | 카탈로그 | — |
| **판매 조건** | `maxOccupancy`, 요금, 재고, 조식 | **live. null 이면 거부** | — |
| 표시 | `propertyName`, `roomTypeName` | **카탈로그** | drift 진단 |

**조건부 폴백을 두지 않는다.** 소스가 섞이는 지점이 곧 불일치가 숨는 지점이다.

```
카탈로그 maxOccupancy = 2, live = null, adults = 3
→ 폴백하면 "2인실인데 3명 검색 결과에 나옴"   ← 자기모순
```

**인원 적합 판정은 공급사가 이미 수행했다.** 우리가 다시 하지 않는다.

---

## Step 6. 요금은 무손실 방향으로만

```
일별 → 총액 : Σ(단가 + 세액). 계약이 보장한다. 무손실
총액 → 일별 : 정보가 없다. 불가능
```

총액만 주는 공급사라면 `StayPrice.totalOnly(total)`,
일별을 가진 공급사라면 `StayPrice.itemized(total, tax, breakdown)` 을 쓴다.

**총액을 박수로 나누지 않는다.** 그렇게 만든 금액은 어느 날에도 실재하지 않고,
검색 금액과 예약 금액이 달라지는 사고로 이어진다.

세액을 모르면 `Optional.empty()` 다. **0 이 아니다.**

가정이 깨지면 추측해서 메우지 말고 `CONTRACT_ASSUMPTION_BROKEN` 으로 거부한다 —
데이터가 잘못된 게 아니라 우리 가정이 깨진 것이므로 지표에 뜨면 코드를 고쳐야 한다.

---

## Step 7. 목록 API 도 같은 함정이 있다

검색 경로만 보고 목록 API 를 대충 넘기면 안 된다.
**본문 코드로 실패를 알리는 공급사는 목록에서도 그렇게 한다.**

목록 API 의 실패를 놓치면
→ 실패 응답이 "숙소 0개" 로 해석되고
→ **빈 스냅샷이 유효한 전체 스냅샷으로 적용되어 그 공급사의 모든 매핑이 비활성화되고**
→ 다음 검색부터 그 공급사가 통째로 사라진다.

빈 스냅샷을 유효하게 받기로 한 결정이 이 판정을 **더** 중요하게 만든다.

`items` 가 `null` 인 것과 빈 배열인 것을 구분한다. 후자만 유효한 0개 스냅샷이다.

## Step 8. 테스트

새 공급사를 추가하면 최소한 이만큼은 있어야 한다.

| 대상 | 확인 |
|---|---|
| 정규화 (순수 함수) | 기준 예시 금액이 그대로 나오는가. 컨테이너 없이 밀리초 |
| 실패 표현 | 그 공급사의 실패가 A·B 와 **같은 `FailureType`** 으로 접히는가 |
| 봉투 | 성공 코드인데 데이터가 없는 계약 위반을 잡는가 |
| 목록 API | 실패를 "0개" 로 오해하지 않는가 |
| 배칭 | 그 공급사의 벌크 상한 경계에서 정확한가 |
| 필드 부재 | 명시적 `false`/`0` 과 구분되는가 |

기존 테스트 중 **하나도 고치지 않아야 한다.** 고쳐야 한다면 공급사 추가가 기존 동작을
바꿨다는 뜻이고, 그건 ACL 이 새고 있다는 신호다.

## 답변 원칙

- **"공급사마다 다르니 분기하죠" 라고 답하지 않는다.** 분기가 필요해 보이면 그것이
  정규화에서 흡수되어야 할 차이인지 먼저 판단한다.
- 새 필드를 도메인에 추가하자는 제안은 **모든 공급사가 그 정보를 주는지** 먼저 확인한다.
  한 공급사만 주는 정보를 필수 필드로 만들면 나머지가 전부 거부된다.
- 이름을 계약보다 앞세우지 않는다. 계약에 없는 개념을 이름으로 도입하면 모델이 사실보다
  넓게 말하게 된다 (`RatePlan` 대신 `OfferConditions` 를 쓴 이유).
- 기존 어댑터를 고쳐야 한다는 결론이 나오면 **그 사실 자체를 먼저 보고한다.**
